# Authentication

Three separate trust relationships, one per hop, none of them sharing a credential:

```
  browser  --[ subscription key + access token ]-->  API Management
  gateway  --[ user-assigned managed identity  ]-->  App Service
  backend  --[ user-assigned managed identity  ]-->  Azure SQL
```

**The running system holds no password.** Not in configuration, not in Key Vault, not in an
environment variable. The SQL server has Entra-only authentication, so a SQL password does not
merely go unused — one cannot be created.

Two credentials *are* used at deployment time, and they are described honestly in §9 rather than
rounded away.

---

## 1. The two things a caller presents, and why they are two

Every call through the gateway needs an **APIM subscription key**. Placing an order also needs an
**Entra ID access token**.

They do not do the same job.

| | Subscription key | Access token |
|---|---|---|
| Answers | *which client and product is calling* | *who is calling and what they may do* |
| Issued by | API Management | Entra ID |
| Lifetime | never expires until revoked | ~60–90 minutes |
| Carried in | `Ocp-Apim-Subscription-Key` | `Authorization: Bearer` |
| Enforced by | APIM's product subscription check | `validate-jwt` at the operation |

**The key gives access to the API. The token lets you place an order.**

A key proves nothing about identity: it never expires and says nothing about what the holder may
do. Treating it as a credential is the mistake this split exists to avoid.

### Anonymous browsing, sign-in at checkout

| Endpoint | Key | Token |
|---|---|---|
| `GET /api/v1/menu` | required | — |
| `POST /api/v1/coupons/validate` | required | — |
| `POST /api/v1/orders` | required | **required**, with `scp` containing `Orders.Write` |

Nobody should have to sign in to look at a menu, and it means the app works the moment it loads.
In APIM, `validate-jwt` is attached to the **`placeOrder` operation**, not to the API — which is
a better demonstration of policy scoping than one blanket rule, and is also what the design
requires.

### The frontend's subscription key is public, and that is the answer rather than the problem

The React bundle carries an APIM subscription key. A browser cannot hide it; anyone who opens
developer tools can read it.

That is deliberate and consistent with the table above: **a subscription key is a client
identifier and a rate-limit handle, not a credential.** The only mutating endpoint is protected
by something the key is not — an Entra access token carrying `Orders.Write`, validated at the
gateway. What the exposure costs is that `GET /menu` and `POST /coupons/validate` can be called
by anyone who extracts the key. Both are read-only, and one of them is a deliberately anonymous
endpoint.

The alternative — dropping `subscriptionRequired` for the frontend — was rejected: it trades a
documented, bounded exposure for an undocumented one, and contradicts the brief's requirement
that the APIs be secured.

**Two separate subscriptions exist**, `frontend` and `smoke-test`, so they are independently
revocable: rotating a leaked frontend key does not blind the pipeline's own verification. Both
keys are generated by APIM, read with `listSecrets` at the moment they are needed, and never
written to a file or published as a pipeline variable.

## 2. The two app registrations

Both are single-tenant (`AzureADMyOrg`) and both are **Day 0** artifacts — created by hand,
because app registrations live in Microsoft Graph rather than in ARM.

| Registration | Purpose | Application (client) ID |
|---|---|---|
| `coupon-api` | The API. Exposes the `Orders.Write` scope. | `90a27142-cffb-4879-873a-bc0a99112ce7` |
| `coupon-spa` | The React frontend. Public client, PKCE. | `04a724e0-6bd9-4285-ab7f-b00d2ce30e2c` |

Application ID URI: `api://90a27142-cffb-4879-873a-bc0a99112ce7`.
Tenant: `8edd202c-5474-4669-9b35-253da7a27cd2`.

`Orders.Write` is granted tenant-wide with `consentType: AllPrincipals`, so no user meets a
consent prompt on first sign-in.

None of the four GUIDs above is a secret. A client ID is a public identifier — it appears in
every token the API issues.

### `accessTokenAcceptedVersion` is 2, set before the first token was ever issued

`coupon-api` has `api.requestedAccessTokenVersion = 2`, set at creation rather than after a
failed policy.

Without it, the v2 token endpoint still returns a **v1** token, whose issuer is
`https://sts.windows.net/{tenant}/` — note the trailing slash. `validate-jwt` compares the issuer
as an exact string, so the mismatch produces a 401 that reads as a broken policy. Setting it
first means the token that gets decoded during development is the token the policy will
eventually see.

### The redirect URIs go on the SPA platform

The required end state on `coupon-spa`:

```
spa           = ["http://localhost:5173",
                 "https://stcouponsvclabdtjori.z29.web.core.windows.net"]
publicClient  = []
web           = []
```

Both URIs under `spa`, no trailing slashes, the localhost one kept **alongside** the deployed one
rather than replaced.

All three platforms accept the same string, and only one of them works:

- **`publicClient`** looks interchangeable — neither platform holds a secret — and Entra accepts a
  browser origin there. Sign-in then fails, because **Entra enables CORS on the token endpoint
  only for redirect URIs registered under `spa`.** A browser redeeming an authorization code
  against `/token` from a `publicClient` URI is blocked by the browser itself. `publicClient` is
  for native and mobile clients, which redeem from a process that has no origin.
- **`web`** expects a confidential client and requires a client secret to redeem the code. A
  browser cannot hold a secret, which is the entire reason this project uses PKCE.

The failure is silent until sign-in, which is why it is written down here. Deployment mechanics
for setting it — including the two `az` commands that appear to work and do the wrong thing — are
in [deployment.md](deployment.md) §2.

## 3. Browser to gateway — authorization code with PKCE

`@azure/msal-browser` and `@azure/msal-react`, redirect flow.

A browser cannot keep a secret, so the client-credentials flow is not available to it. PKCE
proves that the app finishing the sign-in is the app that started it: the client generates a
random verifier, sends its hash with the authorization request, and presents the verifier when
redeeming the code. An intercepted authorization code is useless without it.

### Redirect, not popup

Popups are blocked by default under some enterprise policies and behave poorly on mobile Safari,
and a blocked popup looks like a sign-in button that does nothing — a failure with no error
message anywhere. Redirect works everywhere.

**What redirect costs, and how it is paid.** The round trip to `login.microsoftonline.com`
reloads the page and discards React state, so without persistence a customer would authenticate
*in order to buy a basket* and come back to an empty one, at the worst possible moment. The
basket is persisted in `sessionStorage`, which survives the navigation because it is scoped per
origin per tab and the tab outlives the redirect.

`sessionStorage` rather than `localStorage`: a basket is a per-visit thing and should not still
be there tomorrow. MSAL's own token cache is in `sessionStorage` for the same reason — tokens
live no longer than the tab.

**The basket stores quantities only.** No price is held client-side, so there is nothing there to
tamper with and send back.

### Nothing renders until `handleRedirectPromise()` resolves

On the way back from Entra the URL fragment carries the authorization code. Rendering before MSAL
has processed it shows a signed-out UI for a moment, and any component reading the account list
sees none — so the app would flash "Sign in to order" at somebody who has just signed in.

### Where sign-in happens

Nowhere on load. `placeOrder` calls `loginRedirect` only when the customer actually places an
order, because that is the only endpoint that needs a token. If a silent token acquisition later
fails with `InteractionRequiredAuthError` — consent changed, session revoked, or simply time —
the recovery is `acquireTokenRedirect`, not an error message.

## 4. What the gateway checks

`infra/policies/orders-validate-jwt.xml`, attached to the `placeOrder` operation:

| Check | Value | Why |
|---|---|---|
| **audience** | `90a27142-cffb-4879-873a-bc0a99112ce7` | The token was issued for *this* API. Without it, any valid token from the tenant is accepted, including one issued for a completely unrelated app. |
| **issuer** | `https://login.microsoftonline.com/8edd202c-.../v2.0` | It came from this tenant, via the v2 endpoint. |
| **scope** | `scp` contains `Orders.Write` | The caller holds the permission the operation requires. |

Audience is the check most often missing from copied examples, and it is the one that matters
most.

### Every value came off a decoded token

None of them was predicted. Observed during the PKCE spike, decoded in the browser rather than
pasted into a third-party site:

| Claim | Observed |
|---|---|
| `aud` | `90a27142-cffb-4879-873a-bc0a99112ce7` — the **bare client ID** |
| `iss` | `https://login.microsoftonline.com/8edd202c-.../v2.0` — no trailing slash |
| `scp` | `Orders.Write` |
| `ver` | `2.0` |
| `roles` | absent — correct for a delegated flow |

**`aud` is the bare GUID, not the `api://` URI, and the two are not interchangeable.** Entra can
issue either form depending on token version and how the scope was requested; this tenant, for a
v2 token, issues the bare GUID. Writing `api://90a27142-...` into `<audience>` would produce a
401 that reads as a broken policy rather than as a one-token mismatch. Do not "correct" it.

### The child element order is schema, not style

`validate-jwt` requires its children in this order:

```
openid-config, issuer-signing-keys, decryption-keys, audiences, issuers, required-claims
```

Putting `issuers` before `audiences` is rejected at save time:

```
The element 'validate-jwt' has invalid child element 'audiences'.
List of possible elements expected: 'required-claims'.
```

Worth knowing because the Microsoft documentation contradicts itself here: two samples on the
AI-APIs authorization page show `issuers` first and would be rejected exactly this way. The
policy statement block is the schema; a sample is not.

## 5. The two tokens problem

A single request to `POST /orders` involves **two different tokens**, and both have to be right:

| Token | Obtained by | Validated by | Carries |
|---|---|---|---|
| The caller's | The React app, via PKCE | `validate-jwt`, at the operation | `scp = Orders.Write` |
| The gateway's | APIM's user-assigned identity | App Service Easy Auth | no `scp`; app-only |

They occupy the same header, and the order in which APIM's policies run means the second
overwrites the first.

### The ordering trap, and the fix

`authentication-managed-identity` replaces the `Authorization` header with the gateway's own
token, and it **can only run in `inbound`**. Inbound sections run outermost-first — API scope
before operation scope — so it necessarily runs *before* the operation-scope `validate-jwt`.

If `validate-jwt` then read the `Authorization` header, it would be validating the gateway's own
token rather than the customer's. **And it would pass.** An order endpoint that accepts every
request while reporting successful token validation is the worst available version of that bug,
and no status-code smoke test would catch it.

So the API-scope policy captures the caller's bearer token into a variable *before* the overwrite,
stripping the `Bearer ` prefix:

```xml
<set-variable name="callerToken" value='@{
    var auth = context.Request.Headers.GetValueOrDefault("Authorization", string.Empty);
    return auth.StartsWith("Bearer ", System.StringComparison.OrdinalIgnoreCase)
        ? auth.Substring(7).Trim()
        : string.Empty;
}' />
...
<authentication-managed-identity resource="..." client-id="..." ignore-error="false" />
```

`authentication-managed-identity` is the last statement in inbound at API scope. The operation
policy then reads the stashed value with `token-value` rather than `header-name` — a documented
alternative, and the documentation is explicit that the value must not include the `Bearer `
prefix.

An **empty** `callerToken` for a caller that sent no token is correct and deliberate:
`validate-jwt` fails an empty token value with the configured 401, which is exactly what the
smoke test asserts.

### The evidence that it actually reads the caller's token

Both possibilities return 401, so the smoke assertions alone cannot tell them apart. Application
Insights records the validation failure reason, and that *does* discriminate:

```
placeOrder | TokenNotPresent at validate-jwt | JWT not present.
placeOrder | Invalid JWT. at validate-jwt    | IDX12741: JWT must have three segments
```

The first is the no-token case. "JWT not present" means an **empty** value was validated. Had the
policy read the header, it would have found the gateway's token there — a real, well-formed,
three-segment JWT — and failed on a missing claim instead.

The second rejects the literal string `not-a-real-token` for having no segments. The gateway's
token has three.

Both are only explicable if the value under validation came from the caller.

## 6. Gateway to backend

API Management authenticates to the App Service with a **user-assigned managed identity**. The
App Service allows that one client and nothing else.

```
authsettingsV2:
  requireAuthentication:        true
  unauthenticatedClientAction:  Return401
  clientId:                     90a27142-...          (the coupon-api registration)
  openIdIssuer:                 https://login.microsoftonline.com/8edd202c-.../v2.0
  allowedAudiences:             [ 90a27142-..., api://90a27142-... ]
  allowedApplications:          [ <the gateway identity's client ID> ]
```

`allowedApplications` is what pins the backend to the gateway. A token that is valid for
`coupon-api` but was issued to any other application — including a *user* token from the SPA — is
rejected, because its `appid` is not on the list.

**No third app registration is needed.** Easy Auth reuses `coupon-api`, which keeps Day 0 at
three items. Two things make that work without any directory grant: a managed identity can obtain
an app-only token for `coupon-api` without an app-role assignment (client credentials returns a
token with no `roles` claim, and `allowedApplications` does not look at roles), and a user token
for the same audience is still rejected on `appid`.

`allowedAudiences` carries **both** the bare GUID and the `api://` form. The spike observed the
bare GUID for a v2 token; the `api://` form is how the resource is requested. Accepting both
removes a class of 401 that reads as a broken policy. The gateway itself requests the bare
application ID, which is what the documented example for a caller's own Entra application uses.

`backendResource` and `apiClientId` are separate Bicep parameters holding the same GUID,
deliberately. One is what the gateway asks Entra for; the other is the audience a caller token
must carry. Collapsing them would hide that they answer different questions.

### Why user-assigned, not system-assigned

Both identities in this system are user-assigned. The obvious choice does not work, for two
reasons and the second is the deciding one.

**A system-assigned identity exposes no client ID to ARM.** It surfaces only `principalId` and
`tenantId`. The client ID is needed twice — as the SQL contained-user SID, and in Easy Auth's
`allowedApplications` — and recovering one from a principal ID means `az ad sp show`, a Microsoft
Graph call. The pipeline's service principal has no Graph application permissions and gets
`Authorization_RequestDenied`. Granting some would add a fourth item to the Day 0 list, which is
the thing that list exists to prevent.

**A system-assigned identity dies with its App Service.** Recreate the app alone and the client ID
changes while the *name* does not — so the SQL contained user, matched by name, survives carrying
a SID that no longer belongs to anything. The app then fails to authenticate, and it fails in a
way that reads as a firewall or connection-string problem. On a project whose acceptance test is
"delete the resource group and re-run the pipeline", that is disqualifying.

A third benefit fell out of it: creating both identities in their own module, before anything
consumes them, removes what would otherwise be a circular reference — the App Service's auth
settings need the gateway's identity, and the gateway needs the App Service's hostname.

## 7. Backend to database

The App Service reaches Azure SQL as its own user-assigned managed identity. The connection
string carries no credential and no client ID:

```
Server=tcp:<server>.database.windows.net,1433;Initial Catalog=<db>;
Authentication=Active Directory Default;Encrypt=True;TrustServerCertificate=False;
```

One app setting completes it:

```
AZURE_CLIENT_ID = <the api identity's client ID>
```

`Active Directory Default` resolves `DefaultAzureCredential`, which on App Service picks the
*system-assigned* identity with nothing else configured. With a user-assigned identity there is
no single obvious identity to resolve, so it has to be named. A client ID is a public identifier,
not a credential. Without this setting the first failure is a login failure from the application
with a perfectly correct connection string, which is a bad place to start debugging.

### The contained user is created from a SID, not from Entra

The usual route is blocked:

```sql
CREATE USER [my-app] FROM EXTERNAL PROVIDER;
```

That makes SQL look the identity up in Entra ID, which requires the SQL Server to hold the
**Directory Readers** role — a tenant-administrator grant, which cannot be done from an
application pipeline and on someone else's tenant may not be possible at all.

Supplying the SID directly skips the lookup entirely:

```sql
CREATE USER [id-couponsvc-lab-api] WITH SID = 0x<client-id-as-bytes>, TYPE = E;
ALTER ROLE db_datareader ADD MEMBER [id-couponsvc-lab-api];
ALTER ROLE db_datawriter ADD MEMBER [id-couponsvc-lab-api];
```

**The SID is the client ID, not the object ID.** This is the opposite of the rule everywhere else
in Azure. For RBAC role assignments you use the object ID; for a SQL contained user, users and
groups use the object ID but a service principal — which a managed identity is — uses the
**application (client) ID**. Using the object ID creates a user that exists and then fails to
authenticate.

**Byte order matters.** A GUID's first three fields are little-endian; the last eight bytes are
not:

```
af355f87           ->  875F35AF
3f9a               ->  9A3F
4bb3               ->  B34B
b8f9ea1dc1f2f687   ->  unchanged
```

Derived with `[guid]::ToByteArray()`. String manipulation produces a SID that looks plausible and
silently fails.

To run that statement the pipeline must be an Entra administrator on the SQL Server — one Bicep
property, plus a firewall rule allowing Azure services. The administrator's `sid` in
`Microsoft.Sql/servers` is the **object** ID (the resource schema says so), which the pipeline
obtains by base64-decoding the payload of its own ARM access token and reading the `oid` claim.
That needs no directory permission at all, which is the same constraint that drove the
user-assigned identity decision.

### `SUSER_SNAME()` returns the client ID, not the user name — and that is correct

**Worth knowing before it looks like a bug.**

Because the user was created from a SID rather than `FROM EXTERNAL PROVIDER`, SQL never asked
Entra for a display name. So the login surfaces as `<client-id>@<tenant-id>`:

```
SELECT SUSER_SNAME(), USER_NAME(), DB_NAME();

af355f87-3f9a-4bb3-b8f9-ea1dc1f2f687@8edd202c-...   id-couponsvc-lab-api   sqldb-couponsvc-lab
```

`USER_NAME()` returns the expected name. `SUSER_SNAME()` reads as if a completely different
principal connected.

Anyone diagnosing a managed-identity SQL connection reaches for `SUSER_SNAME()` first, so a
perfectly healthy connection presents as the wrong principal. It is not documented anywhere
obvious. **Read `USER_NAME()`**, and check role membership as well as the login, because that
proves the `db_datareader`/`db_datawriter` grants landed rather than merely that the connection
opened.

### The grant script compares SIDs, not names

`infra/scripts/grant-db-access.sql` reads the existing user's SID and drops and recreates the
user if it differs, printing which of its three paths it took.

An earlier version checked only `WHERE name = @AppName`. That is idempotent for a re-run and
*wrong for a rebuild*: if the identity is recreated the client ID changes and the name does not,
so the old script would find a user with the right name, do nothing, and report success. The App
Service would then fail to authenticate with nothing in the pipeline log pointing at the grant —
that stage was green. The symptom appears one stage later as a failed application start, or later
still as a 500 from a deployed app.

## 8. What is proven, and what is not

The pipeline's smoke test makes four gateway assertions, and every one of them is a **negative**:

| # | Call | Asserted |
|---|---|---|
| 1 | `GET /menu`, no key | 401, body naming the missing subscription key |
| 2 | `GET /menu`, with key | 200, body containing a known pizza name |
| 3 | `POST /orders`, key but no token | 401, body carrying the `validate-jwt` message |
| 4 | `POST /orders`, key and malformed token | 401 from the gateway |

Assertion 2 is the one positive: `/menu` returns 200 only if Easy Auth accepted the gateway's
token, and it runs the same API-scope policy, so **the gateway-to-backend hop is proven by the
pipeline**.

**The positive caller path is not covered by the pipeline.** No automated assertion covers a
*valid* caller token producing a 201, because that needs a real user token, which needs an
interactive PKCE sign-in, which cannot be done from a pipeline agent without storing a credential.

This matters more than it looks: if the policy were reading the `Authorization` header instead of
`callerToken`, it would be validating the gateway's own app-only token, which has no `scp` claim —
so it would *also* return 401, every assertion above would still pass, and the endpoint would be
permanently broken for every real user.

### The positive path, verified manually

Run on **2026-08-28** from a local `npm run dev` against the deployed gateway, signing in through
the real PKCE flow. These are the values the dev-only panel decoded out of the live access token —
the panel's third column prints the token's own claim values, not the expected ones:

| Claim | Observed on the token | Pinned by the deployed policy |
|---|---|---|
| `aud` | `90a27142-cffb-4879-873a-bc0a99112ce7` | `<audience>90a27142-cffb-4879-873a-bc0a99112ce7</audience>` |
| `iss` | `https://login.microsoftonline.com/8edd202c-5474-4669-9b35-253da7a27cd2/v2.0` | `<issuer>https://login.microsoftonline.com/8edd202c-5474-4669-9b35-253da7a27cd2/v2.0</issuer>` |
| `scp` | `Orders.Write` | `<claim name="scp">` → `<value>Orders.Write</value>` |
| `roles` | absent | no `roles` block — correct for a delegated flow |
| `ver` | `2.0` | — |

`Order #2` was created: subtotal €31.50, discount €3.15, total €28.35 — the server's own figures
for 2× Margherita and 1× Veggie Supreme with `PIZZA10`.

**The right-hand column was read back from API Management, not from the repository**, so it is the
policy that actually ran rather than the one in source control. The same read confirms the
attribute that matters most:

```
token-value="@((string)context.Variables.GetValueOrDefault<string>("callerToken", ""))"
```

`token-value`, not `header-name`. That is direct evidence for what §5 previously established only
by inference from Application Insights: the deployed policy validates the caller's stashed token,
not the gateway's managed-identity token that replaced it in the `Authorization` header.

So the full chain is confirmed end to end: a user token carrying `Orders.Write` passes
`validate-jwt` at the operation, the gateway's managed-identity token passes Easy Auth at the
backend, and the App Service reaches SQL as its own identity to price and persist the order.

**What remains a limitation is the automation, not the behaviour.** Reproducing this is a manual
step; closing it properly means a browser-driven test in the pipeline, which is the first item in
[assumptions.md](assumptions.md) §4. The Application Insights evidence in §5 is what covers the
gap between runs.

### The development-only claims panel

The frontend has a token claims panel that decodes a live access token and displays `aud`, `iss`,
`scp`, `roles` and `ver`. It exists precisely because every automated assertion on the token
policy is a negative, and a negative passes identically whether the policy is correct or reading
the wrong token. Checking the claims before trusting a 201 is what tells those apart.

On a deployed site it is a screenshot waiting to happen, so it is not hidden behind a runtime
flag. Its single call site is guarded by `import.meta.env.DEV`, which Vite replaces with the
literal `false` in a production build; the branch becomes dead code, Rollup removes it, and the
module has no other importer, so it is tree-shaken out entirely.

**"It should be stripped" is not a claim worth making unchecked**, so it is verified twice: the
frontend stage greps `dist/` for the marker `PIZZASHOP_DEV_ONLY_TOKEN_CLAIMS_PANEL` and fails the
build if it is present, and the smoke test fetches the *deployed* bundle over HTTP and greps the
served bytes.

## 9. Where credentials do appear

The claim about the running system is absolute. The claim about the pipeline is narrower, and it
is worth stating precisely rather than rounding up.

**Two credentials are used at deploy time.** Both are fetched from ARM at the moment they are
needed, used inside a single task, and never written to a file or published as a pipeline
variable.

**The APIM subscription keys**, read with `listSecrets` — one for the smoke test, one compiled
into the frontend bundle. The design requires them; see §1.

**The storage account key**, used to upload the frontend to `$web`. This one reverses an earlier
decision and the reversal is the interesting part.

Writing blob *content* is a data action that Contributor does not include, so the pipeline
briefly assigned itself Storage Blob Data Contributor in Bicep. That deployment failed before
touching a single resource:

```
InvalidTemplateDeployment: Authorization failed for template resource of type
'Microsoft.Authorization/roleAssignments' ... does not have permission to perform action
'Microsoft.Authorization/roleAssignments/write'
```

Contributor is `*` minus its notActions, and `Microsoft.Authorization/*/Write` is on that list.
*Checking that a principal can perform an operation is not the same as checking it can grant
itself the permission for that operation* — and a role assignment inside a template fails the
entire deployment rather than degrading.

Making it succeed would mean granting the service connection **User Access Administrator**: the
standing power to assign itself any role, on anything, permanently, for the benefit of one file
upload. The account key grants nothing new — Contributor already includes
`Microsoft.Storage/storageAccounts/listKeys/action` — so this principal can mint the key whenever
it likes. Fetching it adds no capability; it only makes an existing one visible.

So the comparison is not "a key versus no key". It is "use a credential the principal can already
mint, or permanently grant it the right to escalate its own privileges". The key wins on the
security argument, not on convenience.

**The claim that survives, and it is the one worth making:** *no secret is stored anywhere, and no
credential is used that the deploying principal could not already obtain.* The passwordless story
for the running system is untouched — this is a deployment-time credential, not a runtime one.

If the service connection is ever given User Access Administrator for other reasons, the role
assignment becomes free and `allowSharedKeyAccess` can be set to `false` on the storage account,
closing the key off entirely. The Bicep comment says so at the property.

## 10. Debugging: who rejected the request

Read the response before changing anything. Routing happens **before** authentication in APIM, so
a 404 means the path did not resolve and no policy ran at all.

| What you see | Who rejected it |
|---|---|
| `"missing subscription key"` | APIM — the key check |
| The `validate-jwt` message naming `Orders.Write` | APIM — the token policy |
| `WWW-Authenticate: Bearer realm="<app>.azurewebsites.net"` | The backend — the gateway's own token failed |
| `403` with an empty body | The backend — gateway known, not on `allowedApplications` |
| `404` from APIM with no backend headers | Path matched no operation; **no policy ran** |
| `AADSTS50011` in the browser | The redirect URI does not match the registration, character for character |

**Access tokens expire.** A call that worked and now returns 401 from the gateway is almost
certainly an expired token — re-issue before debugging anything else. The observed lifetime was
**82 minutes**, not the round hour: Entra randomises access token lifetime between roughly 60 and
90 minutes so that fleets of clients do not re-authenticate in lockstep. The heuristic holds; the
exact number does not.

**A policy change is not testable before deployment.** APIM validates policy content only at save
time — `az bicep build`, `az deployment group validate` and `what-if` all pass a policy the
resource provider will reject. Budget a provision cycle per policy change, or attach the policy
to a scratch API in the running instance first to get the error in seconds rather than minutes.

**Policy placeholders are `__NAME__`, never `{{NAME}}`.** Double braces are APIM's own named-value
syntax, and a policy containing an unresolvable named value is rejected when it is saved.
